# 1. What are first class functions

    In JavaScript, first-class functions mean that functions are treated like any other value (such as numbers or strings).

    That means functions can:
    - ✅ Be assigned to variables
    - ✅ Be passed as arguments to other functions
    - ✅ Be returned from other functions
    - ✅ Be stored in arrays or objects

# 2. Explain Execution context & call stack

i. What is Execution Context?

    An Execution Context is the environment where JavaScript code is evaluated and executed.

There are 3 types:

    1. Global Execution Context (GEC)

    - Created when the JS file first runs

    - There is only one
    - this refers to the global object (window in browsers)
    - Variables and functions declared globally live here

    2.  Function Execution Context (FEC)

    - Created every time a function is called
    - Each function call gets its own separate context
    - Has its own: variables, args, this

    3.  Eval Execution Context

    - Created inside eval() (not commonly used).

Each execution context has two phases:

    - Creation Phase (Memory Phase)
        - Allocates memory for variables → initialized as undefined
        - Stores function declarations fully in memory
        - Sets up the scope chain
        - Determines this

    - Execution Phase
        - Code runs line by line
        - Variables get actual values
        - Functions execute

ii. What is the Call Stack?

    The Call Stack is how JavaScript keeps track of execution contexts.
    It works like a stack (LIFO – Last In, First Out).
    Execution Context is where code runs.
    Call Stack is how JavaScript manages those contexts.

# 3. Hoisting & TDZ

    What is Hoisting?

    Hoisting means that during the creation phase of execution, JavaScript moves declarations (not initializations) to the top of their scope.

    What is TDZ (Temporal Dead Zone)?

    The Temporal Dead Zone (TDZ) is the time between when a variable is hoisted and when it is initialized

# 4. Currying in JavaScript

Currying is a technique where a function with multiple arguments
is transformed into a sequence of functions,
each taking one argument at a time.

Normal function without currying

```js
function add(a, b) {
  return a + b;
}

add(2, 3); // 5
```

Curried version

```js
function add(a) {
  return function (b) {
    return a + b;
  };
}

add(2)(3); // 5
```

    Why Is This Useful?
    - Code reusability
    - Creating specialized functions
    - Functional programming
    - Partial application

# 5. pure vs impure functions

    A function is pure if:
    - ✅ It always returns the same output for the same input
    - ✅ It has no side effects

```js
function add(a, b) {
  return a + b;
}

add(2, 3); // 5
add(2, 3); // 5 (always same result)
```

    What is an Impure Function?
    - Output is not predictable
    - It causes side effects
    - A side effect means: Modifying a global variable, Changing an object/array, Making API calls, Logging to console, Reading current time, Generating random numbers, DOM manipulation

```js
let count = 0;

function increment() {
  count++;
}
```

# 7. Shallow vs deep copy

    - Shallow copy

    Copies only the first level. Nested objects are still referenced (shared).

```js
const user = {
  name: "Alice",
  address: {
    city: "New York",
  },
};

const copy = { ...user }; // shallow copy

copy.name = "Bob";
copy.address.city = "Los Angeles";

console.log(user.name); // "Alice" ✅ (separate)
console.log(user.address.city); // "Los Angeles" ❌ (changed!)
```

    - Deep Copy

    Copies everything, including nested objects. No shared references.

```js
const user = {
  name: "Alice",
  address: {
    city: "New York",
  },
};

const deepCopy = structuredClone(user);

deepCopy.address.city = "Los Angeles";

console.log(user.address.city); // "New York" ✅
```

# 9. optional chaining

    Optional chaining lets you safely access deeply nested object properties
    without throwing an error if something is null or undefined

```js
const user = {
  name: "Alice",
};

console.log(user.address.city);
// ❌ TypeError: Cannot read properties of undefined

// Solution: Optional Chaining
console.log(user.address?.city);

// If address exists → returns city
// If address is null or undefined → returns undefined
```

# 10. nullish coalescing

    The nullish coalescing operator (??) returns the right-hand value only if the left-hand value is null or undefined

Basic syntax

```js
value ?? defaultValue;
// If value is null or undefined → return defaultValue
// Otherwise → return value

let name = null;

console.log(name ?? "Guest");
// "Guest"
```

# 11. Garbage collection

    Garbage Collection (GC) is the automatic process by which JavaScript
    frees memory that is no longer being used.

    (or)

    Garbage Collection in JavaScript is an automatic memory management process
    that removes unreachable objects from memory using a mark-and-sweep algorithm.

- Why Do We Need Garbage Collection?

  When you create variables, objects, arrays, etc., they occupy memory. If unused memory is not cleaned:
  - Memory keeps increasing
  - App slows down
  - Eventually crashes

- How Garbage Collection Works Internally

  Most JS engines use: `Mark and Sweep Algorithm`
  - Step 1️⃣ Mark -> Start from "roots" (global scope), Mark everything that is reachable.
  - Step 2️⃣ Sweep -> Delete everything NOT marked.

# 12. weak references

    A weak reference in JavaScript is a reference to an object that does not prevent it from being garbage collected. It is implemented using WeakMap, WeakSet, or WeakRef.

    If the object becomes unreachable elsewhere → Garbage Collector can delete it even if a weak reference exists.

    JavaScript Provides Weak References Through:
    1. WeakMap
    2. WeakSet
    3. WeakRef

# 13. Streams in JS

    Streams in JavaScript are objects that allow reading or writing data in chunks instead of loading the entire data into memory at once.

    Why Do We Need Streams?

    If you load large data everything at once → 💥 memory issue.
    Streams solve this by processing data as it arrives.

```js
const fs = require("fs");

const stream = fs.createReadStream("bigfile.txt");

stream.on("data", (chunk) => {
  console.log("Received chunk:", chunk);
});
```

    Types of Streams (Node.js)
    1️⃣ Readable Stream :
    Used to read data.

    fs.createReadStream("file.txt");

    2️⃣ Writable Stream :
    Used to write data.

    fs.createWriteStream("output.txt");

    3️⃣ Duplex Stream :
    Can read AND write.

    4️⃣ Transform Stream :
    A special duplex stream that modifies data.

    Real-World Example
    When you watch Netflix:
    - Video doesn’t download fully first
    - It streams chunk by chunk
    - That’s stream in action

# 14. backpressure in streams

    Backpressure is a mechanism in streams that prevents a fast data producer from overwhelming a slow consumer by pausing and resuming data flow.

    Imagine
    - Readable sends 100 chunks/sec
    - Writable can handle only 10 chunks/sec
    - Extra 90 chunks pile up in memory
    - That’s backpressure.

    Without handling backpressure:
    - Memory usage increases
    - App slows down
    - Can crash the server

```js
const fs = require("fs");

const readStream = fs.createReadStream("bigfile.txt");
const writeStream = fs.createWriteStream("output.txt");

readStream.pipe(writeStream);
```

    When you use .pipe():
    ✔ Node automatically handles backpressure
    ✔ It pauses reading if writing is slow
    ✔ Prevents memory overflow

-> How Node Handles Backpressure

```js
// Writable streams return a boolean from .write():
const canWrite = writable.write(chunk);
// true → continue writing
// false → STOP, buffer full
// If it returns false:
// Wait for "drain" event
```

Manual Example

```js
readable.on("data", (chunk) => {
  const canContinue = writable.write(chunk);

  if (!canContinue) {
    readable.pause();
  }
});

writable.on("drain", () => {
  readable.resume();
});
```

    Real-World Analogy -> Netflix streaming:
    - Your internet = producer
    - Your device = consumer
    - If internet sends too fast → device buffers
    - If device slow → internet slows sending

    If device slow → internet slows sending, So producer and consumer stay balanced.

Where Backpressure Matters Most

- File streaming
- Network sockets
- API data transfer
- Video streaming
- Large database exports

# 15. Event Loop

    The Event Loop is the mechanism that continuously checks the call stack and task queues, pushing queued callbacks into execution when the stack is empty.

    JavaScript Is Single-Threaded
    - JS runs on one main thread.
    - One task runs at a time
    - It cannot do multiple things simultaneously

The 3 Main Components

- Call Stack
  -> `Where functions execute.`
- Web APIs (Browser/Node APIs) -> `Handles async tasks like: setTimeout,fetch,DOM event`
- Callback Queues -> `Where completed async callbacks wait.`

### How Event Loop Works (Step by Step)

```js
console.log("Start");

setTimeout(() => {
  console.log("Timeout");
}, 0);

console.log("End");
```

Execution Flow

    Step 1️⃣
    -> console.log("Start")
    -> Goes to Call Stack
    -> Prints Start

    Step 2️⃣
    -> setTimeout()
    -> Goes to Web API
    -> Timer starts

    Step 3️⃣
    -> console.log("End")
    -> Executes immediately
    -> Prints End

    Step 4️⃣
    -> Timer finishes
    -> Callback goes to Callback Queue

    Step 5️⃣
    -> Event Loop checks:
    -> Is Call Stack empty?
    -> Then moves callback to Call Stack
    -> Prints Timeout

    Final Output
    Start
    End
    Timeout

### Important: Microtask vs Macrotask

    There are two main queues:

    1. Macrotask Queue (Callback Queue)
        Includes:
        -> setTimeout
        -> setInterval
        -> setImmediate
        -> DOM events

    2. Microtask Queue (Higher Priority)
        Includes:
        -> Promise.then
        -> Promise.catch
        -> queueMicrotask
        -> MutationObserver

    (Microtasks run before macrotasks)

# 16. de-optimization & why deleting object properties hurts performance

`De-optimization` occurs when a JavaScript engine abandons optimized machine code due to unpredictable object shapes or types. Deleting object properties hurts performance because it changes the object’s hidden class and forces slower dictionary-mode lookups.

### How JS Engines Optimize Objects

Engines like V8 use something called `Hidden Classes (Shape Optimization)`

    When you create objects with the same structure
    - Engine optimizes this layout internally like a class.
    - Fast property access

    What Happens When You Delete a Property?
    - Now the object’s structure changes.
    - The hidden class is broken.
    - Engine can no longer use the optimized structure
    - It switches object to dictionary mode (slower lookup). That’s de-optimization.

### Better Alternative to delete

```js
// Instead of
delete user.age;

// use
user.age = null;
// or
user.age = undefined;
// Structure stays same → no deopt.
```

### Other Things That Cause De-optimization

- Adding properties dynamically after creation

```js
const obj = {};
obj.a = 1;
obj.b = 2;
```

- Changing property types

```js
obj.count = 10;
obj.count = "ten"; // type change
```

- Using try/catch in hot paths
- Using arguments object heavily
- Mixing different object shapes in same function

# 17. Promises

A `Promise` in JavaScript is an object that represents the eventual result of an asynchronous operation. It can be in one of three states: pending, fulfilled, or rejected.
Promises help avoid callback hell and make async code more readable using .then(), .catch(), and async/await.

### It’s mainly used to handle asynchronous operations, like

- Fetching data from an API
- Reading files
- Waiting for a timeout
- Database queries

### Promise States

- Pending
- Fulfilled
- rejected

```js
const myPromise = new Promise((resolve, reject) => {
  let success = true;

  if (success) {
    resolve("It worked!");
  } else {
    reject("Something went wrong.");
  }
});
```

### Useful Promise Methods

- `Promise.all()` -> Waits for all promises to resolve.

  ```js
  Promise.all([promise1, promise2]).then((results) => console.log(results));
  ```

- `Promise.race()` -> Returns the first promise that finishes.
  ```js
  Promise.race([promise1, promise2]).then((result) => console.log(result));
  ```

## 18. Throttling

    Throttling is a technique used to limit how often a function executes over time. It ensures the function runs at most once in a specified interval, improving performance in high-frequency events like scroll or resize

### Why Do We Need Throttling?

Some events fire very frequently, like:

- scroll
- resize
- mouse move
- key up

Without throttling, your function could run hundreds of times per second, causing:

- Poor performance
- Laggy UI
- High CPU usage

Throttling improves performance by controlling execution frequency.

# 21. Error Boundaries in React (JavaScript)

### What Are Error Boundaries?

    Error Boundaries in React are class components that catch JavaScript errors in their child component tree during rendering and lifecycle phases. They prevent the entire app from crashing by rendering fallback UI. They use getDerivedStateFromError and componentDidCatch methods. However, they don’t catch errors in event handlers or async code. They are essential for building resilient production-grade applications.

### How Do You Create an Error Boundary?

    Only class components can be error boundaries (as of now).

    They must implement one or both of:

```js
static getDerivedStateFromError(error)
componentDidCatch(error, errorInfo)
```

```js
import React from "react";

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    // Update state to render fallback UI
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    // Log error to monitoring service
    console.error("Error caught:", error, errorInfo);
  }

  render() {
    if (this.state.hasError) {
      return <h2>Something went wrong.</h2>;
    }

    return this.props.children;
  }
}

export default ErrorBoundary;
```

Usage

```js
<ErrorBoundary>
  <MyComponent />
</ErrorBoundary>
```

### How It Works Internally

When a child component throws during render:

    1. React pauses reconciliation.
    2. It walks up the Fiber tree looking for the nearest error boundary.
    3. It invokes: getDerivedStateFromError(), then componentDidCatch()
    4. The boundary re-renders with fallback UI.
    5. The rest of the app remains intact.

# 22. Controlled and uncontrolled components

### Controlled Components

    A controlled component is a form element whose value is controlled by JavaScript (usually React state).

    How it works:
    - The input value is stored in state.
    - Every change updates the state.
    - The state controls what appears in the input.

```js
import { useState } from "react";

function ControlledInput() {
  const [name, setName] = useState("");

  return (
    <input type="text" value={name} onChange={(e) => setName(e.target.value)} />
  );
}
```

| Pros                     | Cons                       |
| ------------------------ | -------------------------- |
| Easy validation          | More code                  |
| Instant feedback         | re renders on every change |
| predictable behavior     |                            |
| Better control over data |                            |

### Uncontrolled Components

    An uncontrolled component stores its own state internally in the DOM.
    Instead of using state, you use a ref to access the value when needed.

```js
import { useRef } from "react";

function UncontrolledInput() {
  const inputRef = useRef();

  const handleSubmit = () => {
    console.log(inputRef.current.value);
  };

  return (
    <>
      <input type="text" ref={inputRef} />
      <button onClick={handleSubmit}>Submit</button>
    </>
  );
}
```

| Pros                                       | Cons                            |
| ------------------------------------------ | ------------------------------- |
| less code                                  | Harder to validate in real-time |
| Slightly better performance in large forms | Less predictable                |
| Easier for simple forms                    |                                 |
