# 1. What is Event Delegation?

Event delegation is a technique where we attach a single event listener to a parent element instead of attaching listeners to multiple child elements. It works because of event bubbling, where an event triggered on a child propagates up through its ancestors. Inside the parent's event handler, we use event.target to determine which child element was clicked and perform the appropriate action. This approach improves performance by reducing the number of event listeners, simplifies code maintenance, and automatically supports dynamically added elements. A common example is attaching one click listener to a list container to handle clicks on all current and future list items.

# 2. Why does event delegation improve performance?

Because instead of creating hundreds or thousands of event listeners (one per child element), we create only one listener on the parent. This reduces memory usage, speeds up initialization, and simplifies event management, especially when elements are added or removed dynamically.

# 3. Debouncing vs Throttling

| Debouncing                                                                   | Throttling                                         |
| ---------------------------------------------------------------------------- | -------------------------------------------------- |
| Executes **after the user stops** triggering the event for a specified delay | Executes **at most once** every specified interval |
| Waits until the activity has finished                                        | Continues executing at regular intervals           |
| Best for reducing unnecessary API calls                                      | Best for limiting execution frequency              |
| Example: Search input                                                        | Example: Scroll, resize, mouse movement            |

# 4. useEffect vs useLayoutEffect

| `useEffect`                                  | `useLayoutEffect`                                     |
| -------------------------------------------- | ----------------------------------------------------- |
| Runs **after** the browser paints the screen | Runs **before** the browser paints the screen         |
| Does **not** block painting                  | **Blocks** painting until it finishes                 |
| Best for API calls, subscriptions, timers    | Best for DOM measurements and synchronous DOM updates |
| Better for performance                       | Can hurt performance if overused                      |

# 5. CSR vs SSR vs SSG ISR

| Rendering Type                            | HTML Generated                     | Best For                                    | SEO          | Initial Load |
| ----------------------------------------- | ---------------------------------- | ------------------------------------------- | ------------ | ------------ |
| **CSR** (Client-Side Rendering)           | Browser                            | Dashboards, SPAs                            | ❌ Poor      | Slower       |
| **SSR** (Server-Side Rendering)           | Server on every request            | Dynamic pages                               | ✅ Excellent | Faster       |
| **SSG** (Static Site Generation)          | Build time                         | Blogs, docs                                 | ✅ Excellent | Fastest      |
| **ISR** (Incremental Static Regeneration) | Build time + periodic regeneration | Mostly static pages with occasional updates | ✅ Excellent | Very Fast    |
